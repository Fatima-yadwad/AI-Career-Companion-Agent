# AI Career Companion Agent

## Milestone 4.4 – RAG and Knowledge Base Documentation

**Project:** AI Career Companion Agent
**Milestone:** M4.4 – Documentation and Final Integration

---

# 1. Overview

The AI Career Companion Agent uses Retrieval-Augmented Generation (RAG) to identify semantically relevant internship and job opportunities from a curated knowledge base.

The RAG pipeline is implemented using:

- JSON job knowledge base
- Semantic chunking
- Sentence Transformers
- `all-MiniLM-L6-v2`
- Normalized embeddings
- FAISS vector search
- JSON metadata
- Structured job records
- Deterministic job-resume matching

The RAG layer is primarily responsible for **retrieving relevant job opportunities**.

The final candidate-job compatibility score is calculated separately by the deterministic matching layer.

---

# 2. Knowledge Base

The primary job dataset is:

```text
data/processed/internship_jobs.json
```

The dataset contains curated internship/job postings used by the system.

The dataset is loaded by:

```text
backend/rag/loader.py
```

The matching layer also uses the same structured job dataset through:

```text
backend/matching/job_loader.py
```

This allows the system to use semantic retrieval for discovery while retaining the complete structured job record for downstream matching.

# 4. Job Dataset Loading

The dataset loader is implemented in:

```text
backend/rag/loader.py
```

The loader determines the project root and constructs the dataset path:

```text
data/processed/internship_jobs.json
```

The file is opened using UTF-8 encoding.

The loader performs basic validation:

1. Verify that the dataset file exists.
2. Load the JSON file.
3. Verify that the root object is a list.
4. Return the job records.

If the dataset is missing, a `FileNotFoundError` is raised.

If the dataset does not contain a JSON list, a `ValueError` is raised.

# 6. Semantic Chunking

Semantic chunks are generated by:

```text
backend/rag/chunker.py
```

The purpose of chunking is to divide each job posting into meaningful sections before generating embeddings.

The current chunking strategy is section-based rather than fixed-size text splitting.

---

# 7. Chunk Types

A job can generate the following semantic sections:

```text id="f4qmb9"
Job Posting
    |
    +-- Job Description
    |
    +-- Responsibilities
    |
    +-- Required Skills
    |
    +-- Preferred Skills
    |
    +-- Qualifications
    |
    +-- Experience Requirements
    |
    +-- Education Requirements
```

Empty sections are skipped.

This prevents empty strings from being inserted into the vector store.

---

# 8. Chunk Metadata

Every generated chunk retains job-level metadata.

Each chunk contains:

- Job ID
- Job title
- Company
- Location
- Section
- Text

For example, a required-skills chunk is represented conceptually as:

```text id="3t7bkg"
job_id
job_title
company
location
section = "required_skills"
text = "Required skills: ..."
```

This metadata allows retrieved chunks to be mapped back to the original job.

---

# 9. Why Section-Based Chunking Is Used

A job posting contains different types of information.

For example:

- The description explains the role.
- Responsibilities describe expected work.
- Required skills identify essential capabilities.
- Preferred skills identify additional capabilities.
- Qualifications describe eligibility.
- Experience and education sections describe formal requirements.

Separating these sections allows the embedding model to represent these semantic concepts independently.

It also allows the retrieval system to identify which section of a job contributed to a search result.

# 10. Embedding Model

The embedding implementation is located in:

```text
backend/rag/embeddings.py
```

The system uses:

```text
all-MiniLM-L6-v2
```

through Sentence Transformers.

The model converts text into numerical vectors suitable for semantic similarity search.

The resulting embedding dimension is:

**384**

---

# 11. Embedding Normalization

The generated embeddings are normalized.

Conceptually:

```text id="j4r1x8"
Text
 |
 v
Sentence Transformer
 |
 v
384-dimensional vector
 |
 v
Normalization
 |
 v
Normalized vector
```

Normalized vectors allow inner-product similarity to correspond to cosine similarity.

This is compatible with the FAISS `IndexFlatIP` configuration used by the project.

# 13. FAISS Index

The vector store uses:

```text
faiss.IndexFlatIP
```

`IP` represents Inner Product.

Because the embeddings are normalized, inner-product similarity corresponds to cosine similarity.

The index stores the numerical vectors while the metadata file stores the information required to interpret each vector.

---

# 14. Vector Store Files

The generated vector store is stored under:

```text
backend/data/vector_store/
```

The main files are:

```text
jobs.index
metadata.json
```

### `jobs.index`

Contains the FAISS vector index.

### `metadata.json`

Contains metadata associated with each vector, including:

- Job identity
- Job title
- Company
- Location
- Section
- Chunk text

---

# 15. Vector Store Validation

The retriever validates the vector store during initialization.

The implementation loads:

```text
jobs.index
metadata.json
```

It then checks:

```text
FAISS index vector count
        ==
metadata record count
```

If these counts do not match, initialization fails.

This prevents the system from silently associating the wrong metadata with retrieved vectors.

# 16. Runtime Retrieval

Runtime retrieval is implemented by:

```text
backend/rag/retriever.py
```

The retriever receives a natural-language query.

Example:

```text
Python machine learning internship with TensorFlow
```

The query is converted into an embedding using the same Sentence Transformer model used to build the index.

---

# 17. Retrieval Pipeline

```text id="qv1d5e"
User / Candidate Query
        |
        v
Query Embedding
        |
        v
all-MiniLM-L6-v2
        |
        v
Normalized 384-D Vector
        |
        v
FAISS IndexFlatIP
        |
        v
Similarity Search
        |
        v
Top-K Chunks
```

The retriever returns the most semantically similar chunks.

---

# 18. Retrieval Output

Each retrieved result contains information such as:

- Job ID
- Job title
- Company
- Location
- Section
- Text
- Similarity score

The similarity score represents the semantic relationship between the query and the retrieved chunk.

The retrieved section is also preserved for evaluation and debugging.

---

# 19. Candidate Query Construction

The matching service constructs a candidate-oriented query using information available in the candidate profile.

The query can contain:

```text
Candidate summary
Skills: <candidate skills>
Target role: <candidate target role>
```

This query is sent to the RAG retriever.

The purpose is to retrieve jobs that are semantically relevant to the candidate's career profile.

---

# 20. Expanded Retrieval

The matching service does not immediately retrieve only the final requested number of jobs.

Instead, it uses:

```text
retrieval_top_k = top_k × 3
```

with bounds between:

```text
5 and 20
```

Conceptually:

```text id="t8b34q"
Requested final results
        |
        v
Expand retrieval pool
        |
        v
top_k × 3
        |
        v
Semantic candidate jobs
        |
        v
Deduplicate
        |
        v
Deterministic matching
        |
        v
Final top-K
```

This provides a larger candidate pool before deterministic job-resume scoring.

---

# 21. Chunk Deduplication

A single job may have multiple retrieved chunks.

For example:

```text
JOB101
  ├── job_description chunk
  ├── required_skills chunk
  └── responsibilities chunk
```

The matching service deduplicates results using:

```text
job_id
```

Therefore, the final matching stage evaluates jobs rather than allowing multiple chunks from the same job to dominate the candidate pool.

---

# 22. Reconstructing Complete Job Records

After semantic retrieval and deduplication, the matching service obtains the complete structured job records.

The complete records are loaded using:

```text
backend/matching/job_loader.py
```

The loader maps job IDs to structured job objects.

This is important because the semantic retrieval result contains only a chunk, while deterministic matching requires complete job information.

---

# 23. RAG and Deterministic Matching Separation

The system intentionally separates two stages:

### Stage 1 — Semantic Retrieval

RAG determines:

> Which jobs are semantically relevant to the candidate?

### Stage 2 — Compatibility Matching

The matching engine determines:

> How well does the candidate match the retrieved job?

This separation makes the architecture easier to interpret and evaluate.

---

# 24. Deterministic Matching After Retrieval

After RAG retrieval, the matching engine evaluates:

- Required skills
- Preferred skills
- Project relevance
- Education
- Experience
- Qualifications

The current weighted formula is:

```text id="qdb8oc"
40%  Required skills
15%  Preferred skills
15%  Project relevance
10%  Education
10%  Experience
10%  Qualifications
--------------------------------
100% Total
```

The final score is calculated deterministically.

---

# 25. Retrieval Similarity vs Match Score

These two values have different meanings.

### Retrieval similarity

Measures semantic similarity between:

```text
Candidate query ↔ Retrieved job chunk
```

### Match score

Measures candidate-job compatibility using the deterministic weighted matching system.

The current implementation records retrieval similarity in the result but does **not** directly include it in the weighted match-score formula.

Therefore:

```text id="k5l7l0"
RAG similarity
     |
     v
Candidate selection / retrieval evidence

Match score
     |
     v
Deterministic candidate-job compatibility
```

This distinction should be preserved when interpreting evaluation results.

# 32. Current RAG Strengths

The current implementation provides several useful properties.

### Section-aware retrieval

Job postings are divided into meaningful semantic sections.

### Metadata preservation

Retrieved chunks retain job identity and source-section information.

### Normalized embeddings

Embedding normalization makes the FAISS similarity configuration compatible with cosine-style similarity.

### Vector-count validation

The retriever checks index and metadata consistency.

### Candidate-pool expansion

The matching service retrieves a larger pool before final deterministic ranking.

### Job-level deduplication

Multiple chunks belonging to the same job are consolidated.

### Structured job reconstruction

Complete job records are loaded before compatibility scoring.

---

# 33. Current RAG Limitations

The current RAG implementation has several limitations.

1. The knowledge base contains a relatively small number of job records.
2. The current chunking strategy is section-based and does not perform advanced semantic or sliding-window chunking.
3. The system uses one embedding model.
4. Retrieval is based on dense semantic similarity without a separate reranking stage.
5. The vector store uses an exact `IndexFlatIP` search configuration.
6. Retrieval quality depends on the coverage and quality of the curated dataset.
7. Retrieval similarity is not currently incorporated into the final compatibility score.
8. No manually labeled large-scale relevance benchmark is currently integrated into the runtime system.

# 35. Retrieval Parameter Considerations

The most important retrieval parameter currently exposed is:

```text
top_k
```

The matching service internally expands the retrieval pool using:

```text
min(max(top_k × 3, 5), 20)
```

This provides a bounded candidate set.

Increasing retrieval size may improve recall but can also increase downstream scoring work.

Therefore, retrieval parameters should be evaluated using both:

- Relevance
- Latency

rather than optimizing either independently.

# 36. Performance Considerations

The RAG retrieval stage is relatively lightweight compared with LLM-based generation.

In the M4.3 performance run, the RAG job-search operation completed in approximately:

**0.068 seconds**

The job-matching operation, which includes retrieval, structured job loading and deterministic scoring, completed in approximately:

**2.435 seconds**

These measurements were recorded during the tested local environment and should not be treated as universal production latency.

# 37. RAG Reliability

The retriever performs several defensive checks.

### Missing index

If the FAISS index is unavailable, initialization fails.

### Missing metadata

If the metadata file is unavailable, initialization fails.

### Index/metadata mismatch

If the vector count differs from the metadata count, initialization fails.

### Empty query

An empty query returns no retrieval results.

### Invalid top-K

The requested top-K value is bounded to a valid range.

These checks reduce the possibility of returning silently corrupted retrieval results.

# 40. End-to-End RAG Example

Consider a candidate with:

```text
Target role:
Machine Learning Intern

Skills:
Python
Machine Learning
TensorFlow
OpenCV
```

The matching service constructs a query similar to:

```text
Candidate summary...
Skills: Python, Machine Learning, TensorFlow, OpenCV
Target role: Machine Learning Intern
```

The query is embedded and searched against the FAISS index.

The system retrieves semantically related job chunks.

The retrieved chunks are deduplicated by job ID.

The complete job records are loaded.

The deterministic matcher then evaluates the candidate against each retrieved job.

Finally, the highest-scoring jobs are returned.

The selected job can then be passed to the Skill Gap, Application and Interview agents.

# 42. Conclusion

The RAG implementation provides the semantic retrieval foundation of the AI Career Companion Agent.

The pipeline consists of:

```text
Curated Jobs
→ Section-Based Chunking
→ Sentence Transformer Embeddings
→ Normalization
→ FAISS Index
→ Semantic Retrieval
→ Job-Level Deduplication
→ Complete Job Reconstruction
→ Deterministic Matching
→ Top-K Recommendations
```

The current implementation uses **102 curated job records, 388 semantic vectors and 384-dimensional `all-MiniLM-L6-v2` embeddings**.

The separation between semantic retrieval and deterministic compatibility scoring makes the system easier to understand, test and optimize.

The RAG layer subsequently provides grounded job context for the specialized career agents, supporting the broader student workflow from job discovery through application preparation and interview practice.
